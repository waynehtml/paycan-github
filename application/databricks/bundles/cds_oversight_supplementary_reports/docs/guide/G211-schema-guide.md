# Schema Developer Guide

This guide shows how to define table and view schema config, create release notebooks for schema creation, and run those notebooks during release.

## Release-First Schema Creation

Pre-create tables and views during release instead of creating them inside runtime ingestion, transformation, file-loading, or publishing tasks. Runtime tasks should reference existing objects and fail clearly when a required object is missing.

This keeps object ownership, permissions, promotion, and reruns predictable across `dev`, `stg`, and `prd`.

## Key Locations

- `conf/oeds/config/schema`: one Python file per table or view definition.
- `src/oeds/domain/utils/schema/schema_deployment_utils.py`: helper used by release notebooks to create tables and views.
- `examples/release`: sample release notebooks for creating tables, creating views, and registering related release assets.

## Define Schema Definitions

Create one schema config file for each table or view under `conf/oeds/config/schema`.

Use the file name, without `.py`, as the object reference:

- table files use the `tbl_` prefix, for example `tbl_customer.py`.
- view files use the `vw_` prefix, for example `vw_customer_summary.py`.
- materialized-view files use the `mv_` prefix, for example `mv_sample.py`.
- references are used by release args, runtime config, and view SQL placeholders, for example `tbl_customer` or `vw_customer_summary`.

Each schema file must export a top-level `DEFINITION` dictionary.

### Table Definition

A table file should define a `StructType` named `SCHEMA`, a table SQL body named `SQL`, and a `DEFINITION` that binds them together.

```python
"""Schema definition for the tbl_customer table."""

from __future__ import annotations

from pyspark.sql.types import LongType, StringType, StructField, StructType, TimestampType


SCHEMA = StructType(
    [
        StructField(
            "customer_skey",
            LongType(),
            False,
            metadata={
                "identity": {"start": 1, "always": True},
                "comment": "Autogenerated customer surrogate key.",
            },
        ),
        StructField(
            "customer_id",
            StringType(),
            False,
            metadata={"comment": "Source system customer identifier."},
        ),
        StructField(
            "customer_name",
            StringType(),
            False,
            metadata={"comment": "Customer display name."},
        ),
        StructField(
            "update_date",
            TimestampType(),
            True,
            metadata={"comment": "Timestamp when the row was last updated."},
        ),
    ]
)

SQL = """
(
{schema},
CONSTRAINT customer_id_not_empty CHECK (customer_id <> '')
)
USING DELTA
TBLPROPERTIES (
    'delta.enableChangeDataFeed' = 'true'
)
"""

DEFINITION = {
    "catalog": "application_cat",
    "database": "oedisint_db",
    "name": "tbl_customer",
    "kind": "table",
    "schema": SCHEMA,
    "sql": SQL,
}
```

`DEFINITION` fields:

- `catalog`: optional logical catalog key, such as `application_cat`. If omitted,
  the manager uses its required physical `default_catalog` unchanged. An explicit
  catalog uses its runtime mapping or the `{env}_{catalog}` convention. Explicit
  `None`, empty strings, and whitespace are invalid.
- `database`: Unity Catalog schema/database name.
- `name`: physical table name.
- `kind`: use `"table"` for tables.
- `schema`: the `StructType` used to render column DDL.
- `sql`: SQL body appended to `CREATE TABLE`, `CREATE OR REPLACE TABLE`, or `CREATE TABLE IF NOT EXISTS`.

### StructType Metadata

Use `StructField.metadata` for supported extended column behavior.

`comment` renders a Databricks column comment:

```python
StructField(
    "customer_name",
    StringType(),
    False,
    metadata={"comment": "Customer display name."},
)
```

This renders as:

```sql
`customer_name` string NOT NULL COMMENT 'Customer display name.'
```

`identity` renders one Databricks identity column:

```python
StructField(
    "customer_skey",
    LongType(),
    False,
    metadata={
        "identity": {"start": 1, "always": True},
        "comment": "Autogenerated customer surrogate key.",
    },
)
```

This renders as:

```sql
`customer_skey` BIGINT NOT NULL GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1) COMMENT 'Autogenerated customer surrogate key.'
```

Identity metadata supports:

- `start`: integer starting value, defaulting to `1`.
- `always`: boolean identity mode. `true` renders `GENERATED ALWAYS`; `false` renders `GENERATED BY DEFAULT`.

Only one identity column is allowed per table. Identity columns must use `LongType` and must be non-nullable.

`default` renders a Databricks SQL default expression after nullability and
before any column comment:

```python
StructField(
    "completed_at",
    TimestampType(),
    False,
    metadata={"default": "current_timestamp()"},
)
```

This renders as:

```sql
`completed_at` timestamp NOT NULL DEFAULT current_timestamp()
```

The default value must be a non-empty SQL expression string. Configuration is
trusted code, so the expression is rendered verbatim. Identity columns cannot
also declare a default.

### Table SQL

Use `{schema}` where the rendered column DDL should appear. The renderer expands the `StructType` into comma-separated Databricks column definitions, including supported metadata.

Add table-level constraints, `USING DELTA`, partitioning, and table properties in the `SQL` body:

```python
SQL = """
(
{schema},
CONSTRAINT customer_id_not_empty CHECK (customer_id <> '')
)
USING DELTA
PARTITIONED BY (customer_id)
TBLPROPERTIES (
    'delta.enableChangeDataFeed' = 'true'
)
"""
```

Use table constraints only for rules that Databricks can enforce at table creation time. Keep detailed validation logic in pipeline code or data quality checks.

### View Definition

A view file should define a SQL body and a `DEFINITION` with `kind: "view"`.

```python
"""Schema definition for the vw_customer_summary view."""

from __future__ import annotations


SQL = """
SELECT
    customer_id,
    customer_name,
    update_date
FROM {tbl_customer}
WHERE customer_id <> ''
"""

DEFINITION = {
    "catalog": "application_cat",
    "database": "oedisint_db",
    "name": "vw_customer_summary",
    "kind": "view",
    "sql": SQL,
}
```

View SQL can reference tables or views by schema file reference using braces. In this example, `{tbl_customer}` resolves to the fully qualified table name using the same catalog mapping as the view destination. Hardcoded catalog names inside SQL are not rewritten.

### Materialized View Definition and Execution

Use `kind="mv"` and a SELECT body with the same reference placeholders as regular
views. `SchemaRegistry.is_materialized_view` identifies this kind; `is_view`
continues to identify regular views only. `full_name` and `short_name` work for
both kinds.

The [sample definition](../../conf/oeds/config/schema/mv_sample.py) aggregates
`amount` by `category` from `{tbl_sample}`. Create the source table first.
Materialized-view creation belongs in release; subsequent refresh calls can run
in data-pipeline tasks after their source updates.

```python
# After %run ../../common in an examples/schema notebook:
from oeds.domain.utils.schema.schema_deployment_utils import SchemaDeploymentManager

ctx = get_job_context()
deployment = SchemaDeploymentManager.initialize(ctx["env"]).get_instance()
warehouse_id = ctx["sql_warehouse_serverless_large_id"]

deployment.create_materialized_view(
    "mv_sample", warehouse_id=warehouse_id, if_not_exists=True
)
deployment.refresh_materialized_view("mv_sample", warehouse_id=warehouse_id)
deployment.refresh_materialized_view(
    "mv_sample", warehouse_id=warehouse_id, full=True
)
```

Creation defaults to `CREATE MATERIALIZED VIEW`. `if_not_exists=True` leaves an
existing object unchanged; `replace=True` uses `CREATE OR REPLACE MATERIALIZED
VIEW`. The two flags cannot be combined. Refresh addresses the existing object
without rendering or changing its SELECT definition. It uses `SYNC` to wait for
completion. `full=True` adds `FULL`; otherwise Databricks selects the refresh
strategy, which is not guaranteed to be incremental.

Both methods return `None`. They reject non-`mv` definitions and propagate
execution failures. With a warehouse ID, `execute_ddl` handles completion and
cancellation using `timeout_seconds=1800` by default. A blank ID is invalid.

For supported serverless notebook compute, omit the warehouse argument on both
creation and refresh:

```python
deployment.create_materialized_view("mv_sample", if_not_exists=True)
deployment.refresh_materialized_view("mv_sample")
```

This route requires an active Spark session and uses `spark.sql()`. It does not
create a session, infer the job-context warehouse, or fall back to another
backend. `timeout_seconds` is only used for warehouse execution; Spark execution
uses the compute's limits. Existing table/view operations still create or reuse
Spark when first executed; manager construction no longer acquires a session.

Use a Unity Catalog-enabled, serverless-enabled workspace and either a Pro or
Serverless SQL warehouse or supported serverless notebook compute. Azure's
notebook support is currently Beta, region-dependent, and requires runtime 18.1
or newer. Refresh must use the same compute type as creation; do not run the
warehouse and notebook examples against the same existing object interchangeably.
The caller needs source read and catalog/schema usage permissions plus target
`CREATE MATERIALIZED VIEW`; refresh permissions depend on the compute route.
See [compute requirements](https://learn.microsoft.com/en-us/azure/databricks/ldp/dbsql/compute)
and [refresh syntax](https://learn.microsoft.com/en-us/azure/databricks/sql/language-manual/sql-ref-syntax-ddl-refresh-full).

The [example notebook](../../examples/schema/materialized_view.py) selects the
job-context warehouse by default and shows the serverless alternative. It is
not registered in deployed jobs. No schedules or asynchronous refreshes are
configured by these methods.

## Runtime Manager Factory

The shared `common.py` notebook initializes `ConfigManager` and then builds the
schema module map for the current driver and environment:

```python
ConfigManager.initialize(job_ctx["env"])
SchemaManager.initialize(
    job_ctx["env"],
    catalog_mapping={
        "fmd_cat": job_ctx["fmd_catalog"],
        "cur_cat": job_ctx["cur_catalog"],
        "bap_cat": job_ctx["bap_catalog"],
        "sup_cat": job_ctx["sup_catalog"],
        "metadata_cat": job_ctx["metadata_catalog"],
        "reference_cat": job_ctx["reference_catalog"],
        "application_cat": job_ctx["application_catalog"],
        "internal_cat": job_ctx["internal_catalog"],
    },
    default_catalog=job_ctx["catalog"],
)
```

Reusable domain modules create a caller-owned manager without accepting an
environment or manager argument:

```python
schema_manager = SchemaManager.get_instance()
print(schema_manager.get_module_map())
```

`get_module_map()` returns a defensive `dict` from each logical schema ref to
its selected full module name. It is intended for discovery diagnostics and can
also be iterated with `.items()` without importing definition modules.

Every initialization discovers a new immutable `ModuleMap` and replaces the
configuration snapshot used by future managers. The active `ConfigManager`
must use the same environment, and retrieval before initialization raises.
Repeated getters return distinct managers, while existing managers retain their
original environment, module map, default catalog, and catalog bindings after
reinitialization.
Catalog mappings are defensively copied into a read-only snapshot. Omitting
`catalog_mapping` on a later initialization clears previous bindings for future
managers and restores environment-prefix resolution for explicit catalogs.
`default_catalog` is required on every initialization and on direct construction.
Omitting it raises `TypeError`, as do `None` and other non-string values. Blank
strings raise `ValueError`; surrounding whitespace is trimmed. Validation failures
leave the previous configuration intact.

Schema discovery records the effective modules selected by `ConfigManager`
without importing their definitions. `find(ref)` imports and validates only the
requested module. SQL rendering resolves referenced dependencies through the
same lazy lookup path.

Definitions directly under `oeds.config.schema` are shared. A module under
`oeds.config.schema.<environment>` replaces the shared module with the same
basename, while environment-only and shared-only modules are retained. An
override supplies a complete `DEFINITION`; fields are not merged.

### Runtime Catalog Bindings

`common.py` supplies `job_ctx["catalog"]` as the required `default_catalog`.
Definitions can omit `catalog` to use that complete physical name:

```python
DEFINITION = {
    "database": "oedisint_db",
    "name": "tbl_customer",
    "kind": "table",
    "sql": "(customer_id STRING) USING DELTA",
}
```

With `catalog="tst_run_042_cat"` in the job context, this definition resolves to
`tst_run_042_cat.oedisint_db.tbl_customer`. No mapping or environment prefix is
applied to the default. Views and referenced objects use the same omission rule
independently; an explicit catalog on a referenced object still takes precedence.
`resolve_catalog()` continues to require an explicit non-empty logical catalog.
Permission allowlists remain explicit and must allow the resolved physical
catalog; configuring a default does not add an allowlist entry.

`catalog_mapping` maps logical catalog keys to complete physical catalog names.
The schema manager never adds an environment prefix to mapped values. Unmapped
keys retain the existing `{env}_{catalog}` convention. `env` still selects
environment-specific definition modules; a test catalog does not change it.

The shared notebook binds all eight configured catalogs to their corresponding
job-context parameters, as shown in the initialization mapping above.
`application_cat` uses `application_catalog`. Callers assigning a test
catalog must supply that parameter to override application schema destinations.
The separate `catalog` parameter configures project storage roots and supplies
the default for schema definitions that omit `catalog`.

For example, with `application_catalog="tst_run_042_cat"`, a view and its logical table
reference resolve together:

```sql
CREATE OR REPLACE VIEW tst_run_042_cat.oedisint_db.vw_customer_summary AS
SELECT * FROM tst_run_042_cat.oedisint_db.tbl_customer
```

Domain, metadata, reference, and internal source definitions resolve to their
respective job-context catalogs. Logical catalogs outside the configured mapping
retain the environment-prefix fallback.

Keys and values must be strings. Surrounding whitespace is stripped, and the
last entry wins if keys become identical after trimming. Catalog names are not
validated or quoted; callers must supply trusted names compatible with the
deployment and permission helpers, which emit unquoted names. Removing name
validation does not add support for special-character identifiers in those helpers.

`schema_manager.resolve_catalog("application_cat")` exposes the same resolver
used by `find()` to resolve object names for deployment and permission grants.
Schema deployment, logical view references, file loading, and operation-status
table lookup therefore share
the configured destination. This does not rewrite literal SQL, Volume paths, or
other configuration strings, and does not create catalogs or schemas. Provision
the destination catalog/schema and deploy tables before dependent views.

## Create Release Notebooks

Create release notebooks that intentionally create schema objects. The template includes examples in `examples/release`:

- `release-0.0.0-11-create-tables.py`
- `release-0.0.0-12-create-views.py`

Use the table creation notebook before the view creation notebook so views can resolve their dependencies.

### Table Creation Notebook

Basic steps:

1. Load the common notebook and job context.
2. Read `env` from the job context and parse `job_ctx["args"]`.
3. Build the deployment helper.
4. Require `args.ref` and create that one table.
5. Pass `replace` when the release should recreate tables.

```python
from oeds.domain.utils.schema.schema_deployment_utils import SchemaDeploymentManager

args = parse_json(job_ctx.get("args"))
if not isinstance(args, dict):
    raise TypeError("args must be a JSON object")

schema_deployment_manager = SchemaDeploymentManager.initialize(
    job_ctx.get("env")
).get_instance()

ref = str(args.get("ref") or "").strip()
if not ref:
    raise ValueError("args.ref is required")
replace = args.get("replace", True)

logger.info("Creating table: %s", ref)
schema_deployment_manager.create_table(ref, replace=replace)
```

### View Creation Notebook

Basic steps:

1. Load the common notebook and job context.
2. Read `env` from the job context and parse `job_ctx["args"]`.
3. Build the deployment helper.
4. Require `args.ref` and create that one view.

```python
from oeds.domain.utils.schema.schema_deployment_utils import SchemaDeploymentManager

args = parse_json(job_ctx.get("args"))
if not isinstance(args, dict):
    raise TypeError("args must be a JSON object")

schema_deployment_manager = SchemaDeploymentManager.initialize(
    job_ctx.get("env")
).get_instance()

ref = str(args.get("ref") or "").strip()
if not ref:
    raise ValueError("args.ref is required")

logger.info("Creating view: %s", ref)
schema_deployment_manager.create_view(ref)
```

## Run During Release

Run schema creation notebooks as part of the release sequence before runtime jobs depend on the objects.

For tables, use:

```json
{"ref": "tbl_customer", "replace": true}
```

The table release notebook requires one nonblank reference per invocation.

For views, use:

```json
{"ref": "vw_customer_summary"}
```

The view release notebook also requires one nonblank reference per invocation.
